Case study · AI / ML engineering · Oct–Nov 2026

OrderSLM
A small AI model that takes food orders from chat

Customers text restaurants things like "CAN I GET A MEDIUM DRIP COFFE… ACTUALLY MAKE IT 2 MUFFINS". I built a system that turns chats like that into an exact, menu-checked order, using a 0.8-billion-parameter model I fine-tuned that's small enough to run on a laptop. Prices and totals are always computed by code, never by the AI. I measured every choice along the way: which big model teaches best per dollar, which small model learns best, and what shrinking it for deployment costs.

How it works

Chat

Messy, multi-message customer text.

Small model

Proposes the order and the message's intent, quoting the chat for every fact.

Code checks

Items, sizes and add-ons must exist on the menu; anything unknown becomes a question.

Pricing engine

Totals, fees and change in integer cents.

Reply

States only verified facts, asks for what's missing.

The design rule: the AI only proposes. Anything with money or menu facts is decided by tested, deterministic code, so a model mistake turns into a clarifying question, not a wrong charge. A customer saying "I already paid" is recorded as a claim, never as a payment.

How I built it

The approach is distillation: a large, paid model (the "teacher") labels thousands of practice chats, and a small open model (the "student") is fine-tuned to copy it. Then you can run the small one yourself, cheaply and privately. Each step below was a measured experiment.

Step 1 · Test data before anything else

Build the exam first

I designed 3 fictional restaurants (a pizzeria, a burger place, a café) with real menu rules: sizes, add-ons, half-and-half pizzas, combos, delivery minimums. Then I had Claude write conversations from scenario cards and reviewed every expected answer by hand in an annotation tool I built (Preact + FastAPI):

  • Dev: 91 chats, 268 messages
    for tuning prompts and code
  • Fresh: 90 chats, 278 messages
    written after the fixes, to check they generalize
  • Test: 199 chats, sealed
    locked by hash; opened once, at the very end

Step 5 · Fine-tuning (LoRA) on free GPUs

Train, study the mistakes, fix the data, retrain

I trained three students with LoRA (PyTorch, Hugging Face transformers + PEFT) on Kaggle's free T4 GPUs, in resumable sessions under its 12-hour limit. Version 1 got the format right but missed patterns. So I sorted every dev mistake into categories, found that they came from thin training data (e.g. too few "actually, change that" chats), and wrote targeted data for those cases. Version 2, measured on the fresh chats:

Step 6 · A safety net

Can a second model catch the small model's mistakes?

I showed three checkers 42 orders the student got wrong and 42 it got right (with the chat and menu) and asked "does this order match?". A checker that flags most wrong orders but few right ones could trigger a confirmation question only when needed.

Step 7 · Packaging for deployment

Shrink it without losing accuracy

I merged the trained adapter into the model, converted it to GGUF and compressed (quantized) it with llama.cpp, then re-ran every evaluation chat through each version. Columns: fully correct orders on dev and fresh, typical seconds per answer on a T4 GPU and on a 4-core CPU, and peak GPU memory.

  • 8-bit gives identical orders to the original on both sets (not one chat differs), at half the size and 5× the speed.
  • 4-bit saves 0.28 GB more but drops 3 orders per set (not statistically significant), so 8-bit ships.
  • CPU-only is too slow for live chat as measured; most of the time goes to re-reading the long menu prompt. Caching that prompt and Apple Silicon are next.

Engineering highlights

A silent GPU failure, found by a guard

The first packaging run spent 11 hours "on the GPU" while actually running on the CPU: my script had replaced the system's library path, hiding the NVIDIA driver, and llama.cpp fell back without an error. I added stop rules (check the GPU is visible, check memory and speed after the first answer). The next attempt stopped itself in 4 minutes and logged the missing library. The fixed run took 2.2 hours.

Honest evaluation

Separate tuning, fresh and sealed test sets; paired statistical tests with confidence intervals rather than eyeballing; every number regenerated by code from saved run outputs. When a fresh chat led to a fix, its gain is labeled "used for fixes", not reported as a clean result.

Training under a 12-hour limit

Kaggle sessions stop at 12 hours, so training checkpoints itself, including its random-number state, and resumes in the next session. Along the way I fixed an upload that silently dropped subfolders and a resume bug in the random-number state.

Cost discipline

Every paid call was estimated first and logged afterwards from real token counts and verified prices. Total AI API spend so far is $6.63 against a $10 budget. All training and model evaluation ran on free GPUs.
